# Acrodont journeys

A tester's checklist: every journey on the site, walked by hand against a
local `./scripts/dev.py` instance. Working through it should leave you
confident Acrodont can go live. The Playwright journeys (`e2e/`) cover the
same ground automatically. This list is for what a person notices that an
assertion does not: wording, layout, feel, and the phone.

## How to use it

Each item is **Do** something, then **Expect** something. Tick it, or note the
item's ID and what you saw instead. Quoted text is what the page should say.
Do one pass on a desktop browser and one at phone width (about 390 px, with
DevTools' device toolbar or a real phone; see "Setting up").

Update this file with every feature batch.

## Setting up

```bash
./scripts/dev.py --reset --users 1 --scenario studying --scenario finished \
  --scenario segments --scenario trash --scenario saved-searches --scenario limits
```

That gives you:

| What | Where |
|---|---|
| Admin `dev`, password `correct-tile-rack-bingo`; the browser opens signed in as `dev` | dev.py's log |
| A second user, `dev2`, same password | `--login-as dev2`, or log in |
| CSW24 with definitions and leave values, from `fixtures/licensed/` (dev.py downloads it on the first run with `scripts/build-licensed-catalog.py`; if that fails, the test catalog's EN-FIX stands in, and the names below say EN-FIX) | `/admin`, the builder |
| "Studying: CSW24 2–7" (the 20 most probable of each length): Level 1 finished with misses, Level 2 half graded | `/` |
| "Finished: CSW24 sevens" (the 25 most probable) | `/` |
| "Segments: CSW24 2–5 in fives" | `/` |
| "Trashed: CSW24 eights" | the Trash, under the cascades on `/` |
| Three saved searches | the builder's Load dialog |
| Filler cascades until the account holds 90–100% of its 10 MB storage limit, so the Cascades page warns it is almost full (on EN-FIX, whose cascades are a few KB, add `--env MAX_STORAGE_BYTES_PER_USER=100000` to the command above; the figures below then read in KB) | `/` |

For a phone on the same network, start with `BIND_HOST=0.0.0.0` and open
`http://<this machine>:5173`.

Mail never leaves the machine: dev.py prints each confirmation or reset mail
as a link (`[mail] confirm …`, `[mail] reset …`) and any other mail as its
subject (`[mail] to …`). The whole message, body included, is a JSON file in
`.stack/acrodont.outbox/`, named for its recipient; where an item quotes a
mail's text, read it there (the newest file for that address).

## Part 1: visitors

- [ ] **V-1** **Do** open `/` signed out (Log out on the Account page first, or use a private window: `--no-login` only skips dev.py's own sign-in). **Expect** the log-in page, with Create an account; there is no public landing page.
- [ ] **V-9** **Do** log in. **Expect** the Cascades page, the landing page, with New cascade at the top and the Trash below the cascades. An old link to `/trash` lands on the Cascades page, scrolled to the Trash.
- [ ] **V-2** **Do** register a new account. **Expect** "Check your email"; dev.py prints a `[mail] confirm` link; following it confirms the account and lands on the log-in page, which says "Your email address is confirmed. Log in to start.", and you can log in.
- [ ] **V-3** **Do** register with a taken username. **Expect** "That username is taken." under the field, and no mail.
- [ ] **V-4** **Do** register a new username with an address that already has an account (`dev2@acrodont.local`). **Expect** the same "Check your email" page; dev.py prints `[mail] to …: Your Acrodont account`, and that message's body in `.stack/acrodont.outbox/` says the address already has an account.
- [ ] **V-5** **Do** log in with a wrong password ten times in quick succession, then once more. **Expect** "Wrong username or password." each time, then "Too many attempts. Try again in N seconds." (a few seconds: one attempt comes back every six).
- [ ] **V-6** **Do** while signed in as `dev` in another tab, reset its password from "Forgot password?" on the log-in page: ask for `dev@acrodont.local`, follow the `[mail] reset` link, try `dev@acrodont.local` as the new password, then a strong one. **Expect** "If that address has a confirmed account, a reset link is on its way, with the account's username. The link expires in 30 minutes."; the mail's body (in `.stack/acrodont.outbox/`) says "Your Acrodont username is dev."; the link opens "Choose a new password"; the weak password is refused under the field and the same link still works; **Set new password** lands on the log-in page with no message, and the other tab shows "Signed out in another tab" (the reset is a logout on this device; reloading either tab shows the log-in page; a tab in another browser shows "Log in to sync" on its next sync). The new password works, and the old one no longer does. A signed-in user changes it on the Account page instead: **Change password** takes the current password and a new one, a wrong current password or a weak new one is refused under its field, and a change says "Your password is changed. Every other session has been signed out; this one keeps working."; a tab in another browser shows "Log in to sync" on its next sync, a tab in this browser keeps syncing, and the new password logs in.
- [ ] **V-10** **Do** ask for a reset for one address six times within the hour; then open a reset link and submit a weak password six times. The limit is five requests an hour for an address and five from one machine, whatever the addresses, so a request made in V-6 within the hour counts: after it, the refusal comes one request sooner. **Expect** the sixth request from this machine in the hour says "Too many attempts. Try again in N minutes.", for an address with an account or without alike; the link's sixth try says "Too many tries, with this link or from this address. Try again in N minutes, or ask for a new link." (An address gets at most three mails a day from one machine; past that the page answers the same and nothing is sent, so use an address V-4 and V-6 did not.)
- [ ] **V-11** **Do** open `/reset-password/confirm` with no token. **Expect** it says the link is missing its reset token, with a link to ask for a new one, and no form.
- [ ] **V-7** **Do** start with `--env DEV_LOGIN=false --no-login` (a stack with dev log-in never closes registration), fill it to 750 accounts, `MAX_ACCOUNTS` (`docker compose exec postgres psql -U acrodont -c "INSERT INTO users (username, email, password_hash) SELECT 'filler' || g, 'filler' || g || '@example.com', 'x' FROM generate_series(1, 750 - (SELECT count(*) FROM users)) g"`), and register. **Expect** the registration says "Acrodont isn't taking new accounts right now.", for a new address and a known one alike. - [ ] **V-12** **Do** register, then log in before following the link; follow it; follow it again; open `/confirm-email` with no code. **Expect** "Confirm your email address first: follow the link we sent you. ## What a local instance cannot show

- Real mail delivery and the SES bounce and complaint alarms (docs/runbook.md, Alarms).
- Spot interruptions and the circuit breaker (`scripts/check-alerts.sh` tests the alert path).
- TLS, HSTS and Secure cookies: the local stack is plain HTTP.
- Installing on a phone: a phone reaches the local stack over plain HTTP, where browsers register no service worker and offer no install. The iPhone tip and Add to Home Screen need the deployed site (or a phone emulator on `localhost`).

## Known quirks

- `/dev-login` exists in the production build too; on the real site it only says dev sign-in is unavailable, because the endpoint answers 404.
- After `--reset`, a browser that studied before shows the old account's data, with "Log in to sync", until it signs in again: signing in as the same username (dev.py's sign-in does) deletes the old account's data from the device. A username not reused keeps its data until site data is cleared.
